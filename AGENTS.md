# Guidance for future coding agents

## Mission

Build and maintain Tilimyyrä, an independent, open-source civic resource that makes Finnish public procurement understandable and easy to explore. Serve citizens, investigative journalists, researchers and potential suppliers.

Help people answer:

- Who is buying what, in which region, and when can suppliers respond?
- What estimated and awarded amounts are officially reported?
- What does historical purchase-invoice spending show about buyers and suppliers?
- Which notices have documented characteristics that merit closer investigation?

Repository: https://github.com/Savvyboi/procumonitor
Live site: https://savvyboi.github.io/procumonitor/

## Product goals

1. **Make procurement easy to navigate.** Provide fast search, clear CPV-based categories, readable statuses, useful filters, buyer pages, notice details and direct links to official records. Keep notices shareable through URLs.
2. **Make evidence understandable.** Explain values, indicators, source coverage and missing fields in plain language. Distinguish tender estimates, contract awards and actual invoice spending throughout the interface.
3. **Support public-interest research.** Provide CSV/JSON downloads, full-text search, regional and buyer-type feeds, and reproducible data snapshots.
4. **Show useful context.** Enrich Business IDs with official PRH/YTJ records where coverage permits. Present invoice spending as context and attribute a payment to a tender only when a reliable shared identifier supports it.
5. **Remain accessible.** Support mobile and desktop, keyboard navigation, readable contrast, semantic controls and clear loading, empty and error states. Preserve the original language of official notice text.
6. **Stay free and maintainable.** Host on GitHub Pages, ingest through GitHub Actions and keep the application usable from the committed snapshot without an API key.

## Architecture and boundaries

- React, Vite and TypeScript provide the static application; Pagefind indexes generated notice pages.
- GitHub Actions fetches official data, normalizes it, commits public snapshots, builds exports/feeds/search and deploys to Pages.
- The browser reads static artifacts. Authenticated ingestion runs outside the browser.
- Keep deployment compatible with the `/procumonitor/` repository subpath. Use the configured base path for assets, links, downloads, search and feeds.
- Prefer this static architecture. Adding paid infrastructure, a persistent backend or a different hosting provider requires an explicit user decision.
- Keep dependencies and generated artifacts within practical free GitHub hosting limits. Use caching, compression, bounded enrichment and incremental updates.
- Do not edit `dist/` directly; it is generated by the build.

## Official sources

- **Hilma / Hankintailmoitukset.fi:** notices, planning notices and awards. Search summaries and full eForms are separate endpoints. Full content currently arrives as base64-encoded XML inside a JSON response; do not assume the notice itself is JSON.
- **State Treasury / Tutkihankintoja:** official purchase-invoice downloads discovered through the national open-data catalogue. Coverage includes state entities and participating organisations; it is not complete national spending.
- **PRH / YTJ:** official company enrichment by Business ID. Its open-data coverage excludes municipalities, wellbeing services counties and sole traders. Preserve Hilma names when enrichment is unavailable.

Consult `README.md` and the official API documentation before changing source integrations. Verify endpoint and schema changes against actual responses. Preserve source attribution and applicable data licences; the application's MIT licence does not replace source-data terms.

## Data integrity rules

- Publish real official records. Never fill an empty screen with invented tenders, buyers, amounts or metrics presented as real.
- Preserve missing values as `null` or an explicit "not reported" state. A reported zero is different from an unknown value.
- Keep estimated and awarded values and their currencies separate. Aggregate only compatible currencies and label the scope and coverage of totals.
- Invoice accounting lines are not individual invoices or contracts. Include credit notes correctly and disclose withheld supplier identities and incomplete coverage.
- Notice counts are not contract counts. Identify superseded versions using explicit source relationships, not guessed title matches.
- Use performance NUTS geography first, buyer geography as a documented fallback, and allow multiple regions.
- Retain official record identifiers, source links, publication dates and modification dates. Show actual refresh timestamps; scheduled ingestion does not make the site real time.
- Do not infer structured monetary values or bid counts from free-text descriptions without a separately validated method and clear disclosure.
- Keep transparency signals explainable and evidence based. They are investigation prompts, not findings of corruption or wrongdoing.

Current indicator definitions:

- **Single bid:** an award notice with exactly one received tender in at least one lot.
- **Short response window:** deadline minus publication is nonnegative and less than 14 days; amendments can affect interpretation.
- **Near estimate:** a reported EUR award total is 95-100% of a positive notice-level EUR estimate.

If these definitions change, update the implementation, tests and public methodology together.

## Secrets and privacy

- Read the Hilma key only from the `HILMA_API_KEY` process environment or GitHub Actions secret.
- Never put credentials in tracked files, fixtures, logs, browser requests or `VITE_` environment variables. Do not repeat keys from conversation history.
- Send the subscription key only to the intended official Hilma API host.
- Extract only the public procurement fields needed by the site. Do not retain or publish full raw XML payloads or personal contact records.
- Preserve URL validation, XML safeguards and CSV formula-injection protection when changing importers or exports.

## Pipeline expectations

The current defaults are a six-hour schedule, a rolling 180-day notice window, a two-day differential overlap, at most 200 full eForms enrichments per run, at most 100 PRH lookups per run with a 30-day cache, and invoice refreshes at most weekly. These are implementation defaults that may be adjusted deliberately.

- Paginate completely within explicit safety bounds. Respect rate limits and use retries/backoff for transient failures.
- Preserve the last valid snapshot and deployed site when ingestion fails. Never silently replace good data with an empty or partial successful-looking refresh.
- Reuse cached enrichment when source records have not changed. Preserve meaningful publication and modification dates.
- Avoid refreshing large datasets during unrelated interface or documentation changes.
- Scheduled refreshes can create bot commits on `main`; sync before pushing if a refresh may have advanced the branch.

## Working and verification

Use Node.js 22 or later.

```sh
npm ci
npm run dev
npm test
npm run build
npm run preview
```

A normal build uses the committed snapshot and needs no Hilma key. Refresh commands and environment setup are documented in `README.md`.

For data or pipeline changes, add focused tests for material behavior such as missing values, currency compatibility, version relationships, status transitions or malformed source data. Run `npm test` and `npm run build` for application changes. For interface changes, also verify the affected interactions, keyboard use, mobile layout and repository-subpath links in a browser. Documentation-only changes need a content and diff review rather than a full ingestion or build.

Preserve unrelated user changes. Keep this file and the public methodology aligned with implemented behavior. Describe any unimplemented feature or unsupported data relationship honestly; do not present roadmap items as working capabilities.
## Interface and branding

- Brand: **Tilimyyrä**, with a European mole (kontiainen) mascot in public/mole.svg.
- Palette: brown, forest green and cream in light mode; blue-black in dark mode. Preserve readable contrast in both.
- Finnish is the default interface; Swedish and English are available throughout. Keep src/i18n.ts translations complete and preserve the original language of official notice text.
- Keep language, themes and bookmarks persistent where browser storage is available. Preserve migration of bookmarks from the old Avoin storage key.
- Discovery filters and sorting belong in shareable URLs. src/lib/discovery.ts owns matching, Helsinki date boundaries and currency-compatible sorting; test material behavior in tests/discovery.test.mjs.
- Static full-text search and indexed notice pages use scripts/templates/search.html and public/static-pages.*; keep their branding, language controls and themes aligned with the React interface.
